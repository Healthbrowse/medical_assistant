HealthBrowse AI — system design
===============================

HealthBrowse is a research browser for people looking up health information
and for clinicians studying the evidence behind an answer. The browser gives
a direct, cited answer. Buddy carries the question into a conversation, a
six-deck topic overview, or an analysis of a document the reader supplies.

1. Application boundaries
-------------------------

The running application lives in healthbrowse/. The HTML, CSS and JavaScript
desk lives in healthbrowse/dist/. The build packages its assets and shared
request handler into a Worker. Cloudflare can run the Worker directly. The
standalone Node server adapts HTTP requests to that same handler for local
development and container deployments.

The root frontend/ and backend/ belong to the earlier Streamlit/FastAPI
MedQuAD project. The React frontend and FastAPI browser backend are the
capstone migration target. The separate Medical Model Lab has its own model,
data, evaluation and serving entry points.

Request handlers — healthbrowse/worker/routes.mjs and healthbrowse/server/main.mjs
Build — healthbrowse/scripts/build-worker.mjs

2. From question to browser result
----------------------------------

Consider “What is the main function of the pituitary gland?” A reader can
ask this in either audience setting. The subject sends it to medical search.
The audience determines how the answer is written.

1. The desk checks the Supabase session and reads the selected audience.
   The client screens the question for urgent symptoms, identifying details
   and unsafe requests. Ambiguous terms or missing context can open a short
   clarification with selectable answers.
2. Medical search uses POST /api/ai/answer. The server validates the request
   and screens the supplied context along with the question. Before medical
   retrieval, it verifies the bearer token with Supabase and enforces the
   account's request limit.
3. Retrieval starts from relevant local passages and can add live evidence.
   An anatomy question can match an OpenStax passage about normal function.
   The server assigns source identifiers and supplies passages to the model.
4. On the cited generation path, the audience model drafts claims. A second
   model call assesses their support. The server resolves the citations
   against the retrieved records and withholds unsupported claims. If the
   provider or review fails after retrieval, eligible passages can appear as
   labeled excerpts. If evidence is insufficient, the user sees the gap.
5. General readers see a plain-language answer. Clinicians see Clinical
   Synthesis, Evidence Breakdown, and Limitations & Contraindications as the
   material supports them. The result includes links to sources and can add
   suggested reading, a credited illustration or a source-derived diagram.
   The automated checks establish traceability; clinical accuracy still
   requires independent review.

A nonmedical question follows a separate route, POST /api/browser/general.
It uses a curated guide when one matches, or ranks public results from
GOV.UK, Crossref and Wikipedia. This route produces a source-based answer
without calling the medical generation model.

Routing — healthbrowse/dist/response-mode.js and healthbrowse/dist/app.js
Synthesis — healthbrowse/server/model-api.mjs and healthbrowse/server/model-cited.mjs
General search — healthbrowse/server/general-browser.mjs

3. Evidence and model routing
-----------------------------

Bundled evidence includes MedlinePlus topics, selected CDC/NCI material,
historical MedQuAD passages and pinned OpenStax anatomy and physiology text.
Collection scripts preserve source identity and provenance. The scheduled
MedlinePlus refresh proposes a change for review. The application can use
bundled sources when live medical retrieval is disabled.

With the DeepSeek profile and live retrieval enabled, the literature planner
selects searches from public terms and indexed subject headings. A bounded
rule-based plan is available when the model planner fails. The retrieval
service searches MED-indexed Europe PMC records, can follow a cited study,
and checks publication identity. It extracts passages from eligible PMC full
text when reuse terms and identity checks pass. Abstract-only records retain
that label. POST /api/ai/evidence exposes the searches, sources and evidence
gaps as JSON for inspection independently of answer generation.

The example configuration selects these DeepSeek checkpoints through the
Hugging Face inference router:

  General synthesis and review     deepseek-ai/DeepSeek-R1-Distill-Llama-8B
  Clinician synthesis and review   deepseek-ai/DeepSeek-R1-Distill-Qwen-32B
  Literature search planning       deepseek-ai/DeepSeek-V3.2

A deployment can explicitly select Groq or dedicated model endpoints.
GET /api/ai/status shows route configuration. A signed-in test question
with a generated answer and resolved citations checks inference end to end.

Retrieval — healthbrowse/server/live-evidence.mjs and healthbrowse/server/literature-search.mjs
Model selection — healthbrowse/server/model-provider.mjs
Source collection and reuse — healthbrowse/docs/medical-retrieval.md

4. Buddy and file questions
---------------------------

Buddy starts with the active browser question, summary and audience. A
focused follow-up uses the relevant topic and recent conversation context.
A medical topic overview can return six decks with citations and indicate
where evidence is missing. The browser result remains a direct answer.

Buddy’s plus (+) button opens the file picker. The client extracts text from a text-based
PDF, DOCX, PPTX, TXT or Markdown file, or builds an aggregate profile for a
CSV or TSV. The reader previews the content before attaching it. A scanned
PDF needs OCR before this flow. The original file stays in the tab. When
the reader submits a question, the client sends the reviewed extracted
content to the server. It selects supporting passages for the model and
resolves references to pages, slides or sections. An unanswered document
question produces a gap in document evidence.

Client — healthbrowse/dist/buddy.js and healthbrowse/client/file-parser.mjs
Document evidence — healthbrowse/server/document-evidence.mjs

5. Accounts, storage and operations
-----------------------------------

Supabase Auth owns identities and sessions. General and Clinicians are
reading preferences. Model credentials stay on the server. The hosted Worker uses the D1 binding named DB for
workspace records and request quotas. Workspace operations check the
verified user's ownership. Eligible saved chats include their source
references; reopening a chat displays the saved answer. Document turns and
questions flagged as personal are excluded from account chat history.
Personal-input screening has limits. Eligible questions and passages are
sent to the configured model provider for inference.

Authenticated feedback and contact submissions use the workspace database.
Feedback is available for human review. Contact forwarding uses Resend when
configured. The Node server supports a local SQLite workspace when
WORKSPACE_DB_PATH points to a migrated database on persistent storage.
Replicated deployments require a shared, durable workspace backend.

Development and the JavaScript CI job use Node 24. The current Dockerfile
pins a Node 26 image. See healthbrowse/package.json and healthbrowse/Dockerfile.
The Worker exposes GET /healthz for liveness and GET /readyz for required
browser assets. The Node adapter also marks readiness down while draining.
On relevant changes, GitHub Actions builds and tests the application, runs
inference checks, and smoke-tests and scans the container. Cloud Run release
has an explicit deployment gate. The offline red-team suite exercises both
audiences and the browser and Buddy entry points.

Local commands (from healthbrowse/, using Node 24)
    npm ci
    npm run build
    npm test
    npm run qa:red-team
    npm start

Runtime setup — setup.md and healthbrowse/docs/WORKSPACE.md
Deployment — healthbrowse/deploy/README.md

6. Research workflows
---------------------

The earlier MedQuAD pipeline discovers and classifies files in
src/data/load_data.py, then reads the selected formats via src/data/loaders/.
Preprocessing, feature engineering, splitting and evaluation support the
earlier experiments. The SageMaker MedGemma inference job lives in
deployment/medgemma/. The archived HealthBrowse QLoRA evaluations and
release reports live in healthbrowse/inference/.

The independent Medical Model Lab retrieves from its own corpus, validates
training and validation splits, and trains a QLoRA adapter on the pinned
Meta-Llama-3-8B-Instruct base in a separate GPU run. The evaluation compares
base and adapter answers on the same benchmark. Smoke runs check the
pipeline; candidate comparisons and reviewed outputs inform later decisions
about integration. The browser uses its separately configured inference provider.

Lab entry point — healthbrowse_model_lab/README.md
Capstone architecture and experiment protocol — healthbrowse/docs/capstone/
